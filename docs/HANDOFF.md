## 2. The workload (just enough to understand the CI)

A plant electrophysiology sensor front end: a KiCad 9 schematic with 5 sheets (Power, Electrodes, PassiveAFE, EIS,
Digital). It has two modes: passive electrome recording (INA121 → 60 Hz notch → 20 Hz LPF → AD7124 ADC) and EIS
(AD5933 → Howland current source → sense amps). The schematic and simulations were generated by another model;
Trevor's original requirements live in his Claude doc "Plant Sensor CI — Setup Guide (pre-Namespace)".

The pipeline:
1. **ERC:** `kicad-cli sch erc` (passes, 0 errors / 0 warnings in KiCad 9.0.9).
2. **Export:** netlist, BOM CSV (with `Tolerance`/`TempCo` fields), PDF.
3. **Simulate:** 4 ngspice testbenches (`anti_alias`, `buffer`/eis_sense, `excitation`, `reference`).
   - **27 corners** (3 temperatures × 3 supplies × min/typ/max tolerance)
   - **2000-run Monte Carlo** (20 shards × 100 runs, seed 42 + i)
4. **Report:** pass/fail and yield tables, histograms, MC timing.

**Key mechanism:** the schematic is the single source of truth. `run_sim.py` reads the exported BOM and overwrites
each `.param <REFDES>` in the testbenches. The "red test" (C308 47n → 470n in the schematic) correctly fails the
`f3db_hz` and `settle_half_lsb_s` specs.

**Workload shape (why it matters for CI):** corners are tiny (~0.2–0.5 s each). Monte Carlo is the only real CPU
work. Everything else is seconds.

## 4. Current state of the two workflows (as of commit `2305f19`)

Both workflows have the **same 4-job chain**:

```
image ──► erc ──► export ──► sim (27 corners serial + 20 MC shards serial + report, all in one job)
```

| | `ci-baseline.yml` (GitHub) | `ci-namespace.yml` (Namespace) |
|---|---|---|
| runner | `ubuntu-latest` | `namespace-profile-plant-sensor` |
| image builder | `docker/setup-buildx-action@v3` on the runner | `namespacelabs/nscloud-setup-buildx-action@v0` (remote builder) |
| layer cache | `cache-from: type=gha`, `cache-to: type=gha,mode=max` | the remote builder's persistent cache |
| image name | `ghcr.io/trevorfar/plant-sensor-ci-gh:<hashFiles(Dockerfile)>` | `ghcr.io/trevorfar/plant-sensor-ci:<hashFiles(Dockerfile)>` |
| jobs use image via | `container: {image: ${{ needs.image.outputs.image }}, credentials: GITHUB_TOKEN}` | same |
| apt installs per job | none (all in the image) | none |

Both were reviewed and are structurally valid: one of `run`/`uses` per step, no duplicate keys, and every job using
`needs.image.outputs` lists `image` in its own `needs`. The latest runs (`9a30ec4`, `2305f19`) **succeeded on both**.

**Gotchas already hit and fixed (likely to recur):**
- `needs.X.outputs` only works if X is listed **directly** in that job's `needs` (it isn't inherited transitively).
- Steps merged into one by a missing `- ` (gives a step with both `run` and `uses`, plus a duplicate `uses`).
- `steps:` accidentally indented under `outputs:`.
- Typos: `docker/Dockfile`, `unamespace-profile-…` (that one queues forever and never errors).
- A step left with only `name:` (invalid).
- `cache-to: type=gha, mode=max`: the space after the comma breaks it.
- An `upload-artifact` with its `with:` separated from it while comments were being added.

## 5. History of experiments (qualitative findings)

1. **Unoptimised baseline** (GitHub, stock KiCad image + apt in every job). Found that setup dominates the small
   jobs: in `erc`, pulling the image ("Initialize containers") took ~17–20 s for well under 1 s of ERC. apt
   ngspice + Python took ~25–35 s. Monte Carlo was by far the largest step.
2. **Same workflow, Namespace runner swapped in.** Faster overall, mostly in Monte Carlo (CPU) and in container
   start-up. Queue time before the first job is consistently a few seconds *longer* on Namespace (a fresh VM per
   job, presumably).
3. **Prebuilt image on Namespace** (tagged by commit sha at the time):
   - The layer cache clearly works: the cached build was several times faster than the cold one.
   - The image only pays for itself once cached. The cold image job made the run slower than with no image.
   - With a stock image under a *stable* tag, one Namespace job's container start dropped to ~1 s (a cache-volume
     hit). With per-commit tags it never did. → **Tagging switched to `hashFiles('docker/Dockerfile')`** on both
     sides, so the tag only changes when the Dockerfile does.
4. **GitHub optimised to match** (same image job with gha layer cache), so both sides run identical pipelines.
   Runs `2ada952` (cold), `9a30ec4` and `2305f19` (cache) are the first fair comparison. **Trevor is generating
   the new results table from these.**

**Open questions to keep in mind when reading new results:**
- **Namespace profile vCPU count.** GitHub `ubuntu-latest` (public repo) = 4 vCPU. Monte Carlo is CPU-bound, so if
  the Namespace profile is bigger, part of its win is just more cores. Recommended: 4 vCPU for the fair run, then
  try larger profiles as a separate experiment. (Not confirmed what the profile is set to.)
- **Does the Namespace cache volume serve container-job images consistently?** Look at "Initialize containers" per
  job with `verify.py --steps`. Also check that the profile has "Container images" caching ticked.
- **GitHub timings are noisy.** The same MC step has varied about 2× between GitHub runs. Namespace has been steady.
  Use several warm runs per side.
- The first run after any Dockerfile change is cold on both sides. Don't compare cold against warm.

## 6. Tools for measuring

```bash
python3 verify.py                    # latest commit that has runs of BOTH workflows
python3 verify.py --steps            # plus per-step rows (Initialize containers, build-push, MC, …)
python3 verify.py --sha 2305f19      # a specific commit
python3 verify.py --runs ID1 ID2     # specific run ids
```
- **What it shows:** run wall-clock, queue before the first job, total runner time, and per-job wall time.
- **Matrix jobs** ("corners (5)") are grouped, with count, wall span and summed runner time.
- **The last column** is right-vs-left speed-up.
- **Auth:** set `GITHUB_TOKEN` if the repo ever goes private.
- `report.py`'s "Monte Carlo timing" section (in the `sim-results` artifact) gives MC wall vs equivalent serial time.
